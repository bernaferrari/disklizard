## Dependency notes

- **001 first**: it's a data-loss/safety fix and is independent — ship it before
  features that expand deletion surfaces (007).
- **002 before 006/007**: the recognition tests are the safety net for the
  Reclaim engine; land them before extending `recognize.ts` (006) or
  generalizing state around it (007).
- **004 after 003**: both edit `sunburst.ts`; apply 003's scheduler change
  first so 004's `isDiskScanNode` deletion doesn't conflict.
- **005 is independent**: it composes with the existing view toggle and color
  engine; can run any time.
- **005/006/007 are spikes**: their deliverable is a prototype + a defined API
  + open questions, not a finished feature. Read each plan's "spike" framing
  before executing.

## Highest-leverage call-out

**Plan 001 is the most important item here.** The feature advertises deletions
as recoverable ("Move to trash", "restore if needed") but permanently `rm -rf`s.
Until it lands, the Reclaim flow — which actively encourages deleting caches and
build output — is a data-loss hazard. Do that one first.
